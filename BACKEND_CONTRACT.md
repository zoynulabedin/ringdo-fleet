# Ringdo portal integration contract

This frontend is being developed independently while the backend is completed. It does not change the backend repository. API paths below are relative to the server-only `API_BASE_URL` (normally ending in `/api/v1`). Existing means observed in the backend source, not verified against a deployed service.

## Implemented connection

| Portal                    | Source-backed routes used by the frontend                                                                                                                       | Current limit                                                                                                                                                       |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Customer                  | `GET /search/providers`, `/bookings`, `/users/me/wallet`, `/support/tickets`; support ticket messages                                                           | Discovery needs an explicitly chosen point. Service creation waits for verified offer and server quote contracts. Shop checkout is preview only.                    |
| Professional              | `GET /bookings`, `/provider/profile`, `/provider/earnings`, `/provider/capabilities`; `PUT /provider/availability`; booking accept, reject, en-route and arrive | Availability reads the current profile, preserves emergency availability and omits the independently configured coverage. Service catalog editing is preview only.  |
| Driver                    | `GET /provider/vehicles`, `/transport/readiness`                                                                                                                | Preparation only. Public trip creation, acceptance and dispatch remain off.                                                                                         |
| Team                      | `GET /admin/support/tickets`, ticket messages; `POST` ticket messages and AI draft; country capability applications read                                        | Privileged case context is restricted until purpose, case scope and independent grant contracts are integrated. AI text is always a draft requiring human review.   |
| Merchant, Fleet, Business | Common profile and support access only                                                                                                                          | Organization APIs and verified membership scopes have not been supplied. Their operational screens use explicitly selected preview data and disable live mutations. |

Common profile: `GET/PUT /users/me`. OTP auth: `POST /auth/send-otp` with `{phone,country_code}`; `POST /auth/verify-otp` with `{phone,country_code,otp}`. Staff auth: `POST /admin/login` then `/admin/login/2fa` with `{pre_auth_token,totp_code}`. Team rejects password-only sessions. Refresh/revoke: `POST /auth/refresh` and `/auth/logout` with `{refresh_token}`.

Successful responses may use `{success:true,data:...}`. Auth completion needs `{access_token,refresh_token,user:{id,name,role,country_code,language?}}`. List responses may be an array or an object containing `items`, `data`, `bookings`, `providers`, `tickets`, `vehicles` or `messages`. Authorization and resource ownership must be checked by the backend for every request.

## Backend handoff

1. **Membership and bootstrap.** Return the authenticated user's organizations, allowed country/area scopes, workspace permissions and active organization ID. Merchant, fleet and business role names in `app/portal.ts` are proposed placeholders and fail closed until agreed; a UI role must never create membership. Existing professional role is `provider`. Team uses the existing staff roles.
2. **Discovery.** Preserve the buyer's 500 m / 1 km / 2 km / 5 km boundary; do not silently widen it or return unavailable/out-of-coverage sellers. `distance_km` must be authoritative and unrounded. Provider IDs, approximate public `lat/lng`, service category keys, country, availability and coverage decisions are needed. Map graphics are illustrative; server distance and address coverage remain authoritative.
3. **Service offers and quotes.** Versioned catalog, fixed vs diagnosis-plus-quote pricing, inclusions, materials, committed service radius, actual address coverage, taxes, fees, currency, quote expiry, approved extras/change orders, cancellation and refund rules. Use a server-calculated quote and an idempotency key for booking/payment mutations. No client-calculated price authorizes a charge.
4. **Merchant.** Organization-scoped catalog/stock, storefront, opening hours, customers, delivery/pickup choices, order transitions, owned QR/payment instructions and subscription entitlements. Buyer-reported payment, merchant acknowledgement and PSP-verified payment are separate facts. Merchant purchase funds must not become a Ringdo service-wallet balance.
5. **Fleet and driver.** Organization-scoped vehicles, drivers, permits, insurance, assignment conflicts, maintenance and readiness. Sandbox and public release are separate server-enforced states; user edits cannot release a country/area or enable public transport.
6. **Business.** Membership, requester/approver/finance permissions, budgets, approval thresholds, requests, invoice reconciliation and an audit trail. Avoid self-approval and enforce amount/currency and current record versions on the server.
7. **Support.** Confirm pagination, ticket status, assignee and message schema. Any unmasked case context needs scoped authorization, access purpose, independent grants where required, and audit logging. Keep customer-service chat separate from privileged support notes. The current non-team conversation screen represents support tickets.
8. **Remote themes and notifications.** The portal CSS uses semantic variables. Agree the approved theme endpoint/schema and signed-in country/role surface before consuming tokens. Provide authenticated notification reads and acknowledged updates; the live UI currently shows no sample notifications.

## Boundary and deployment notes

- Browser requests go to `/api/backend/*` on the portal origin. The server reads a signed HttpOnly, SameSite cookie and forwards a bearer token only to the configured trusted backend origin. No access/refresh token is returned by page loaders or stored in localStorage.
- Each loader/action authenticates independently. The BFF has a per-portal method/path allowlist, origin checks for writes, bounded JSON bodies and a single refresh retry. It is defense in depth; it does not replace backend ownership, country, organization, grants, rate limits or audit checks.
- Use HTTPS in production, a unique random `SESSION_SECRET` per portal, and one consistent secret across that portal's instances. Auth is unavailable without a 32-character secret. Cookies are signed, not encrypted; keep cookie/header logs redacted. The current refresh deduplication is process-local; use backend rotation grace or shared coordination before multi-instance scale.
- A production reverse proxy must preserve the public request origin (Host and scheme) so same-origin checks work. Do not disable those checks to accommodate a proxy error.
- Preview requires `?preview=1`; `PORTAL_ENABLE_PREVIEW=false` disables it. Preview edits stay in memory and `call()` rejects live API access while preview is selected. Explicit sign-in leaves the preview. Never treat sample amounts, verification badges or readiness as real account data.
- Monetary preview fixtures use integer minor units in BDT. Current source-backed monetary fields are major-unit BDT; agree explicit minor-unit currency schemas before international rollout. Public map positions are approximate, never the service address.
- Configure a licensed production `PUBLIC_MAP_STYLE_URL`, required map-provider browser key restrictions and attribution. The built-in OSM raster fallback is for development, not a production tile capacity commitment. Map failure leaves the results list usable.

## Review checks

`npm run typecheck`, `npm test`, and `npm run build`. Tests cover strict radar limits, coordinate/redirect validation, payment-state wording, role/path/country restrictions, request origins, signed session cookies, API origin configuration and refresh retry against a local mock backend. Live OTP delivery, staff credentials, payments, production maps and backend authorization need staging end-to-end testing after the contracts above are available.
